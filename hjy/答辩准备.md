## 二、选题背景与意义类

### Q1. 为什么选这个题目？解决了什么实际问题？
**答**：现在高校研究生培养中，课程考勤、请假审批、实验室预约这几件事，传统上靠纸质登记、口头通知、Excel 统计，存在三个比较突出的痛点：

1. **流程分散**——考勤、请假、预约分别在不同地方处理，工作量大且容易出错；
2. **反馈滞后**——学生不知道请假有没有批、实验室时段是不是被占，状态不透明；
3. **数据难统计**——实验室真实使用率、爽约情况都没办法量化追踪。

我做这个系统的目标，是把**研究生课程考勤、请假审批、实验室预约、审批、签到签退、使用统计**这条链路整合到一个平台里，形成"申请-审批-履约-统计"闭环，提高管理规范性和资源利用效率。

### Q2. 为什么把"课程考勤"和"实验室预约"两条线整合在一个系统里？
**答**：两条业务在使用人群、权限模型、认证方式上是高度共享的：

- 用户群体重叠：学生既要签到也要预约实验室；教师既审批请假也会预约实验室；
- 权限体系统一：都需要 JWT + RBAC 校验；
- 公共支撑相同：登录、个人中心、工作台都是共用的。

如果拆成两个系统，登录态、用户表、权限校验都要写两遍，反而带来"两个孤岛"。整合在一个平台里既减少重复开发，又给"研究生管理"一个统一入口。但**业务链路本身是独立的**——课程考勤库表（`course`、`course_student`、`course_attendance`、`leave_apply`）和实验室库表（`lab`、`lab_booking`）之间没有交叉外键，模块解耦清晰，后续要拆分也容易。

### Q3. 国内已经有不少实验室预约系统了，你的工作有什么区别 / 价值？
**答**：参考的 22 篇文献里大多数国内系统聚焦在**"预约 + 审批"**这一段，对**"预约之后到底用没用"**很少处理。我这个系统在已有预约能力之上多走了几步：

1. 引入了**签到 / 签退环节**，把预约和实际使用绑定；
2. 提出了**"已生效预约为分母"的真实使用率指标**——避免无法准确还原"理论可用总时段"的问题，更贴近业务含义；
3. 加上**自动爽约识别**和**自动完结**机制（详见 Q14），让统计数据不依赖人工维护。

整体上把实验室管理从"预约系统"做成了"使用闭环 + 数据看板"。

## 三、技术选型类

### Q4. 为什么用 B/S 不用 C/S？
**答**：
- **部署成本**：B/S 浏览器即可访问，无需安装客户端，研究生 / 教师 / 管理员各种设备直接打开就用；
- **维护升级**：服务端统一更新，不需要催用户升级客户端；
- **使用场景**：校园里学生用手机临时签到、老师在办公电脑审批、管理员后台看统计，多终端切换更方便。
- C/S 的优势主要是离线和复杂图形处理，对管理类系统价值有限。

### Q5. 为什么前端选 Vue 3 不选 React / Angular？
**答**：
- **学习曲线和生态**：Vue 模板语法直观，组合式 API（Composition API）也能支持复杂逻辑；
- **生态匹配**：Element Plus 是 Vue 生态里最成熟的后台管理组件库，本系统大量用了表单、表格、对话框、日期时段选择器，配套度高；
- **构建效率**：Vite 比 Webpack 启动快、热更新快，适合毕设这种迭代频繁的场景；
- **响应式系统**：Vue 3 的 Proxy 响应式相比 Vue 2 的 defineProperty 更完整，性能也更好。
- React 同样优秀，但路由（React Router）、状态（Redux/Zustand）、UI 库都要自己拼装，对一个人开发的毕设来说成本更高。

### Q6. 为什么后端选 Spring Boot 不选 Node.js / Django？
**答**：
- **类型与重构**：Java 是强类型，多表关联的复杂业务（预约状态机、考勤回写）改动时编译期就能发现问题；
- **生态成熟**：Spring Data JPA + Spring Security + Spring Web 一站式，做 RESTful API、ORM、过滤器拦截非常顺；
- **企业实践**：高校系统、政府系统普遍用 Java 栈，与"工程实践化"目标一致；
- 与前端 Vue 3 的 axios + JSON 通信，前后端约束清晰。
- Node.js 适合 I/O 密集的场景，本系统更偏 CRUD + 状态机；Django 用得少且非主流。

### Q7. 为什么数据库用 MySQL 不用 NoSQL（MongoDB / Redis）？
**答**：
- **数据特征是结构化的**：用户、课程、预约都有固定字段；
- **强一致性 / 事务**：预约冲突检测、请假审批回写考勤，都要事务保证原子性，关系型 + 事务是天然契合；
- **多表关联**：课表生成、考勤汇总需要 JOIN 多张表，MySQL 一条 SQL 解决，NoSQL 要么冗余存储、要么应用层关联；
- **唯一约束**：可以用唯一索引天然防止重复（比如 `course_student` 的 `(course_id, student_id)` 唯一约束、`course_attendance` 的"课程+学生+日期"业务唯一）。
- Redis 更适合做缓存（论文中"未来展望"里有提，可以缓存课表、热门实验室列表），但作为主存储不合适。

### Q8. JWT 和 Session 的区别？为什么用 JWT？
**答**：
- **存储位置不同**：Session 把会话数据存在服务器（内存或 Redis），JWT 把身份信息以签名后的 Token 形式存在客户端；
- **状态性**：Session 是有状态认证，需要会话存储；JWT 是无状态，服务端只需验签和解析；
- **跨域 / 多端**：Session 依赖 Cookie，跨域多端处理复杂；JWT 通过 HTTP Header 携带，前后端分离场景天然适配。

我用 JWT 的核心原因：
1. 系统是**前后端分离 + RESTful** 架构，无状态认证更契合；
2. 后续如果扩展到多实例部署，服务端不用做 Session 同步；
3. JWT 载荷里直接带 `userId`、`username`、`role`，过滤器里解一次就能给后续业务用，不用再查数据库。

实现：HS256 签名，密钥配置在 `application.yml`（`jwt.secret`），有效期 24h（`expiration-ms: 86400000`），代码位于 `JwtUtil.java` 和 `JwtAuthFilter.java`。

### Q9. RBAC 是怎么实现的？只有三个角色为什么不直接 if-else？
**答**：
- **数据模型**：`sys_user.role` 字段存角色字符串（`student`/`teacher`/`admin`），登录时把 role 写进 JWT 载荷；
- **接口侧（后端）**：每个 Controller 方法调用 `requireAdmin()` / `requireBookingUser()` 等校验方法，方法内部从线程局部 `UserContext` 取角色，与预期不符就抛 `BusinessException(403)`。例如 `LabController.requireAdmin()`。
- **路由侧（前端）**：`router/routes.js` 的 `meta.roles` 数组声明允许角色，`router/index.js` 的 `beforeEach` 全局守卫拦截，无权限直接重定向到首页或登录页；
- **菜单侧**：左侧菜单根据当前角色过滤，不显示无权限入口。

"为什么不直接 if-else"——本质上现在就是 if-else 在落地 RBAC，但**抽象层做得清楚**：
- 角色和权限的映射独立在权限方法里（`requireAdmin`、`requireBookingUser`），不散落在业务代码里；
- 后续要扩展角色（比如"院系管理员"），改权限校验方法和前端 `meta.roles` 即可，不动业务逻辑；
- 没有上 Spring Security 是因为本系统角色固定、权限粒度只到接口级别，引入 Security 会增加配置复杂度，性价比不高，但**架构上是 RBAC 思想**——用户-角色-资源映射。

## 四、系统设计类

### Q10. 系统整体架构是怎样的？说说三层之间怎么协作。
**答**：典型的前后端分离 B/S 三层架构：

```
┌──────────────────┐     ┌──────────────────────┐     ┌──────────────┐
│ 前端表现层 (Vue3) │ ──> │ 后端业务层 (Spring Boot) │ ──> │ 数据存储层 (MySQL) │
│ 浏览器 / Pinia   │ <── │ Controller / Service /  │ <── │ JPA           │
│ Axios            │     │ Repository              │     │              │
└──────────────────┘     └──────────────────────┘     └──────────────┘
       ↑                          ↑
       │  JWT in Header          │  RBAC 权限校验
       └─────────────────────────┘
```

- 前端通过 axios 走 `/api` 前缀，开发期 Vite 反向代理到 `http://localhost:8080`；
- 后端按 Controller / Service / Repository 三层；
- 所有请求经过 `JwtAuthFilter` 统一拦截解析 Token，将身份写入 `UserContext`（ThreadLocal），业务侧通过它做权限判断；
- 数据通过 JPA 持久化到 MySQL。

### Q11. 数据库设计了多少张表？为什么是这些？
**答**：系统核心 **7 张表**，分两条业务域：

| 业务域 | 表 | 作用 |
|---|---|---|
| 课程考勤 | `sys_user` | 用户表，三角色共用 |
| 课程考勤 | `course` | 课程基础信息（学期、起始周、星期、起止时间） |
| 课程考勤 | `course_student` | 选课关系，`(course_id, student_id)` 唯一 |
| 课程考勤 | `course_attendance` | 课程考勤主表，记录每堂课的签到状态 |
| 课程考勤 | `leave_apply` | 课程请假申请，绑定课程和日期 |
| 实验室 | `lab` | 实验室基础信息和状态 |
| 实验室 | `lab_booking` | 预约表，承载状态机和签到签退时间 |

两条业务域**不设交叉外键**，只共用 `sys_user`，模块解耦，便于后期扩展。

> 备注：项目中还保留了一张历史表 `attendance_record`（早期通用考勤表），目前不参与主流程，文档中明确为"兼容保留"。如果老师追问数量不一致，可以这样解释。

### Q12. 课程的"上课日期"是怎么计算出来的？数据库里只有星期和周次吧？
**答**：`course` 表存的是**周期性排课规则**（学期、第一周周一日期、上课周次区间如 `1-16`、星期几、起止时间），具体某个日期是不是有课，要在业务层算：

1. 取 `term_start_date`（第 1 周周一日期）；
2. 用前端传入的目标日期 `targetDate` 计算与起始日的周差 → 算出当前是第几周；
3. 校验：周是否在 `weeks` 区间内；星期是否匹配；课程状态是否 active；
4. 三个条件都符合，才认为当天有该课。

这套规则统一封装在 `CourseService.isCourseActiveOnDate(...)`，签到、请假、考勤查询都复用，**保证排课结果在全系统一致**。

### Q13. 实验室预约状态机有几种状态？怎么流转？
**答**：7 种状态，状态机流转如下：

```
                  pending（待审批）
                 /         \
            approved      rejected
            （已通过）      （已拒绝/终态）
            /     \
       checked_in  no_show
       （使用中）   （爽约/终态）
            |
        completed
       （已完成/终态）

pending --用户主动--> cancelled（已取消/终态）
```

- `pending` 由用户预约提交时写入；
- `approved` / `rejected` 由管理员审批触发；
- `checked_in` 由用户当日到场签到触发（必须在时段开始前 15 分钟到结束之间）；
- `completed` 由用户主动签退，或系统懒刷新"过时段未签退"自动完结触发；
- `no_show` 由懒刷新"过时段未签到"自动转换；
- `cancelled` 仅允许 `pending` 状态下的预约由本人取消。

代码位置：`LabService` 中 `createBooking` / `approveBooking` / `checkInBooking` / `checkOutBooking` / `cancelBooking` / `refreshExpiredBooking`。

### Q14. "懒刷新"是什么？为什么不用定时任务？
**答**：
- **场景**：预约通过审批后没签到、签到后没签退，需要把状态推进到 `no_show` 或 `completed`，否则统计数据不准。
- **常规做法**：用 `@Scheduled` 定时任务每分钟扫一遍状态过期的记录。
- **我用的做法**：在「查我的预约 / 查实验室时段状态 / 查管理员统计 / 签到签退前校验」这些**自然查询入口**触发刷新（`refreshExpiredBookings`）：
  - `approved` 且超过时段结束仍未签到 → 改 `no_show`；
  - `checked_in` 且超过时段结束仍未签退 → 改 `completed`，并把签退时间补成时段结束时刻。

**好处**：实现简单、不依赖调度器、无需考虑节点重启或并发；
**代价**：刷新只在被查询时生效，理论上"长期没人查"的记录状态会滞后，但因为统计入口本身就触发刷新，业务上没有可见影响。
这是一个权衡——毕设系统并发不大、可解释性要求高，懒刷新更合适。

## 五、关键实现类

### Q15. 实验室预约冲突是怎么避免的？并发提交怎么办？
**答**：**两层防护**：

1. **业务层校验**（`LabService.createBooking`）：
   - 用 `existsByLabIdAndDateAndSlotAndStatusIn(labId, date, slot, SLOT_BLOCKING_STATUSES)` 查询，只要存在 `pending`/`approved`/`checked_in`/`completed`/`no_show` 任一状态的记录就视为已占用。
   - 占用状态特意把 `no_show` 也包含进去，**意思是"产生过预约的时段不允许重复占用"**，避免恶意预约-不签到造成的资源浪费数据不一致。
2. **事务保证**（`@Transactional`）：
   - `createBooking` 方法整体在事务里，保证"读检测 + 写入"的原子性；
   - 异常时事务回滚，不留脏数据。

> **关于并发**：现在依赖事务的隔离级别和乐观时间窗，**没有上数据库唯一索引或分布式锁**。如果老师追问严格的并发场景，可以坦诚补充：
> - 当前对单库单实例足够，500 并发测试 0 错误率；
> - 若真要面对极端高并发，可在 `lab_booking` 上加 `(lab_id, date, slot)` 唯一约束（针对非取消/拒绝状态），由数据库层兜底；或上 Redis 分布式锁。这部分在论文未来展望里也提到过。

### Q16. 请假审批通过后考勤状态怎么自动更新？
**答**：在 `AttendanceService.approveLeave(...)` 里实现的（位于 `lamp_back/.../service/AttendanceService.java`）：

1. **审批校验**：先确认是教师本人授课课程（防越权审批）、请假状态是"待审批"、请假记录绑定了课程和日期；
2. **冲突拦截**：先查这个学生当天对应课次的 `course_attendance`，如果已经是「已签到」或「迟到」，**拒绝审批通过**——真实出勤优先级最高，不允许被请假覆盖；
3. **更新请假单**：状态改为「已通过」/「已驳回」，写入审批备注；
4. **回写考勤**（仅审批通过）：
   - 若没有考勤记录则新增一条；
   - 若有"待签到"记录则更新；
   - 字段：`status = "请假"`，清空 `check_in_time`，写入 `remark`；
5. **驳回不动考勤**：仅修改 `leave_apply` 单子状态，`course_attendance` 不变。

这个逻辑把"请假"和"考勤状态"两条数据通过审批动作连接起来，**学生考勤查询返回的状态由 `course_attendance` 和 `leave_apply` 联合决定**（`resolveAttendanceStatus`），保持一致。

### Q17. 课程签到是怎么判定"正常 / 迟到 / 缺勤"的？
**答**：分两个阶段：

**1. 签到当下（写入 `course_attendance`）**：
- 学生提交签到时，业务层校验：选课关系存在、当日是该课程的上课日、当前没有非"待签到"状态记录（防重签）；
- 取签到时刻与课程 `start_time` 对比，**晚于开始时间则记"迟到"，否则记"已签到"**；
- 写入 `check_in_time`。

**2. 查询展示时**：
- 对于历史日期但 `course_attendance` 里没有签到记录的，统一显示为「缺勤」；
- 对于未来日期，显示为「待签到」；
- 对于今天但课程已结束没签到的，显示为「缺勤」；
- 对于审批通过的请假，状态为「请假」。

签到只跟课程时间相关，**不依赖任何位置 / 设备认证**——这是毕设的边界（论文未来展望里有提"可扩展二维码 / 地理围栏"）。

### Q18. 签到 / 签退的时间窗口是怎么设计的？
**答**：
- **签到窗口**：时段开始前 15 分钟 → 时段结束（如 14:00-16:00 的实验室，13:45 起可签到，16:00 后不能首次签到）；
- **签退**：必须先签到，签到后任意时点可签退；如果忘签退，懒刷新会自动补 `completed` 状态并把 `check_out_time` 设为时段结束时刻；
- **必须当天**：跨天签到一律拒绝。

代码位置：`LabService.checkInBooking` 和 `canCheckIn`。前端通过 `canCheckIn` / `canCheckOut` 标志位决定按钮是否可点，提示信息由 `getBookingActionHint` 返回（"开始前 15 分钟内可签到"等）。

### Q19. 登录的完整流程？前后端怎么协作？
**答**：
1. **前端**：用户在 `LoginView.vue` 输入账号密码 → 调用 `authApi.login` → POST `/api/auth/login`；
2. **后端 Controller**：`AuthController.login` 接收账号密码；
3. **后端 Service**（`UserService`）：
   - 按账号查 `sys_user`；
   - 用 BCrypt 校验密码（不区分用户不存在 / 密码错 / 账号禁用的具体原因，统一返回"登录失败"，避免信息泄露）；
4. **生成 Token**：`JwtUtil.generateToken(userId, username, role)`，HS256 签名，24h 有效；
5. **返回**：`{token, user: {id, username, name, role, ...}}`；
6. **前端存储**：`setToken / setUser` 把 token 存到 `localStorage.lamp_token`，user 存到 `lamp_user`；
7. **后续请求**：`axios` 拦截器自动给所有请求 Header 加 `Authorization: Bearer <token>`；
8. **后端拦截**：`JwtAuthFilter`（继承 `OncePerRequestFilter`）拦截所有非 `/auth/login`、`/auth/register` 的请求，解析 Token 后把身份写入 `UserContext` 供业务用；解析失败或缺失返回 401。

### Q20. 前端路由守卫具体怎么做的？
**答**：在 `router/index.js` 的 `beforeEach` 里：

```
1. 取 token：
   - 没 token + 访问白名单（/login、/register）→ 放行
   - 没 token + 访问其他页 → 跳转 /login?redirect=原路径
2. 有 token：
   - 访问 /login → 重定向到首页 /
   - 访问其他页 → 取当前用户角色，检查目标路由 meta.roles
     - 有 roles 限制且不包含当前角色 → 重定向到首页（防越权进入）
     - 否则放行
```

注意点：
- **不只看 token 存在**，还要看角色匹配，避免学生通过手敲 URL 进入管理员页面；
- **后端不依赖前端**，所有受保护接口在后端再校验一次 RBAC（如 `requireAdmin`），防止绕过前端守卫直接调接口。

### Q21. RESTful API 设计举几个例子？
**答**：完全按 REST 风格：

| 方法 | 路径 | 含义 |
|---|---|---|
| GET | `/lab/list` | 实验室列表（分页/筛选） |
| GET | `/lab/{id}` | 实验室详情 |
| GET | `/lab/{id}/slot-status` | 某日各时段占用状态 |
| POST | `/lab/booking` | 创建预约 |
| GET | `/lab/booking/my` | 我的预约 |
| PUT | `/lab/booking/{id}/cancel` | 取消预约 |
| PUT | `/lab/booking/{id}/approve` | 审批预约 |
| PUT | `/lab/booking/{id}/check-in` | 签到 |
| PUT | `/lab/booking/{id}/check-out` | 签退 |
| GET | `/lab/usage/stats` | 使用统计 |

约定：响应统一 `{code, message, data}`；GET 用查询参数，POST/PUT body 用 JSON；动词体现状态变更（cancel / approve / check-in），而不是用 `/api/cancelBooking` 这种"路径里塞动作"的形式。

## 六、安全与合规类

### Q22. 密码怎么存储的？为什么用 BCrypt 不用 MD5？
**答**：BCrypt 加密入库。原因：
- **MD5 / SHA1 是哈希算法，不是加盐密码算法**，加上彩虹表攻击，已不适合直接存密码；
- **BCrypt 内置盐**（每次加密结果不同），慢哈希设计本身抗暴力破解；
- Spring Security 的 `BCryptPasswordEncoder` 已经是行业标准。
注册、修改密码、初始化 admin 全部统一用 BCrypt，避免出现"老接口用 MD5、新接口用 BCrypt"的混乱。

### Q23. Token 被窃取怎么办？
**答**：现在的方案是有边界的，可以坦白：
- **当前防护**：Token 有效期 24h，HS256 签名防伪造；HTTPS 传输（部署时）；
- **不能防的**：一旦 Token 在有效期内泄露，攻击者完全可冒充用户。

可改进方向（论文未来展望里提到）：
1. **短期有效 + Refresh Token**：把 access token 缩到 15-30 分钟，refresh token 单独存储与吊销；
2. **黑名单机制**：登出 / 改密时把 token JTI 写进 Redis 黑名单；
3. **绑定指纹**：在载荷里加 IP / UA 指纹，请求时校验匹配。

这些当前没做，是为了控制毕设复杂度，但架构上是可以平滑加上的。

### Q24. 注册接口怎么防止有人注册成 admin 角色？
**答**：`AuthController.register` 入参校验里**直接拦截 `role = admin` 的请求**——拒绝管理员的自助注册路径。admin 账户由应用启动时检测数据库，不存在则自动初始化（用户名 `admin`，密码 `admin123` 经 BCrypt 加密）。这样**前台注册和后台账户完全隔离**。

### Q25. 越权访问怎么防？前端守卫不就能绕过吗？
**答**：**前后端双层防护**：
- 前端守卫只是用户体验层面的拦截（避免误入无权页面）；
- 真正的安全屏障在后端：每个受保护接口在 Controller 入口处显式调 `requireAdmin()` / `requireBookingUser()` 等方法做角色校验；
- 即使有人通过 Postman 直接打接口，没有合法 Token + 对应角色，照样拒绝。

这一点在论文 5.5 节有明确写："后端不依赖前端权限控制结果，对所有受保护接口单独进行角色校验"。

### Q26. 系统怎么测的？覆盖了哪些场景？

**功能测试**（论文第 6.3 节，共 27 个用例）：

- 考勤管理 8 例（签到、签退、请假、审批、重复签到、非课程时间签到、未签到签退、权限校验）；

- 结果：全部通过。

**性能测试**（论文第 6.4 节）：
- 工具 JMeter，并发用户数 100 / 300 / 500，本地环境；
- 平均响应时间 4~6 ms，吞吐量 ~100 req/s，错误率 0.00%；
- 测的接口主要是高频读：实验室列表查询、预约提交。

### Q27. 500 并发 4ms 响应是不是太理想了？能复现吗？
**答**：要承认这是**本地环境的理想数字**，不是真实生产指标——

- **环境因素**：单机本地、MySQL 也在本地、JMeter 和应用在同一台机器，所以网络几乎没成本；
- **业务复杂度**：被测接口是查询类，查询是建表索引覆盖的，加上 JPA 一二级缓存命中；
- **数据规模**：测试数据量不大，B-tree 索引下查询是 O(log n)。

**真实场景预期**：如果上到独立服务器、走真实网络、数据量上来，响应时间会明显增加（几十到一两百毫秒级），错误率主要会出现在数据库连接池上限、JVM GC 这些地方。但**这个数字至少能说明应用层逻辑没有阻塞 / 锁竞争问题**。下一步如果上 Redis 缓存课表和实验室列表，能进一步降低 DB 压力。

### Q28. 怎么验证预约冲突检测在并发下不出错？
**答**：当前主要靠两点：
1. 业务层用 `existsBy...StatusIn` + 事务保证「读检测 → 写入」原子性；
2. 压测下未发现重复预约（500 并发 0 错误率）。

**严格说**：在没有数据库唯一索引兜底的情况下，理论上极端并发下还存在窗口期问题。**改进方案**就是在 `lab_booking` 加部分唯一索引（针对非取消 / 拒绝状态），由 DB 层兜底，应用层捕获唯一约束异常返回业务错误。这部分如果老师要细抠，可以承认是优化方向。

## 八、亮点与创新类

### Q29. 你觉得这个系统最大的亮点是什么？
**答**：四个亮点（PPT 末页也是这四点）：

1. **分散管理场景集中化**：把课程考勤、请假、实验室预约、签到签退、统计五件事整合到一个平台、统一用户体系，比单做"实验室预约"更完整；
2. **预约冲突检测机制**：「实验室 + 日期 + 时段」三元组占用判定 + 业务层校验 + 事务保护；
3. **实验室真实使用率统计**：引入签到 / 签退，定义"已生效预约为分母"的真实使用率，加上自动爽约和自动完结，形成"预约 → 审批 → 签到 → 签退 → 统计"的数据闭环；
4. **系统架构与安全控制**：JWT + RBAC + 前后端双层权限校验，模块解耦，便于扩展。

### Q30. "真实使用率"分母为什么用"已生效预约数"而不是"理论可用时段数"？
**答**：两种口径各有利弊：

| 分母 | 优点 | 缺点 |
|---|---|---|
| 理论可用时段数 | 反映实验室整体开放率 | 需要历史可用时段快照；维护时段开放规则复杂 |
| 已生效预约数 | 业务可解释：预约后到底用了没；实现简单 | 不反映"没人预约"的实验室浪费 |

我的系统里实验室没有"历史可用时段"的快照，时段是 6 个固定槽位（8 点到 22 点每 2 小时一段），如果用理论分母还要算出维护期、节假日，复杂度上升收益有限。**用"已生效预约数为分母"更贴合"预约-履约率"语义**，可解释性强，毕设亮点呈现更聚焦。

公式：`真实使用率 = 实际使用数(checked_in + completed) / 已生效预约数(approved + checked_in + completed + no_show) × 100%`

## 十、对架构和选型的追问

### Q33. 为什么没有用微服务？
**答**：
- **规模不匹配**：单一学院、用户百余人级别，服务拆分带来的运维 / 监控 / 通信开销远大于收益；
- **业务耦合度低，但流量小**：课程考勤和实验室预约本就解耦，但都跑在一台机器上，没必要拆；
- **学习成本**：微服务还要带服务发现、网关、配置中心、链路追踪，对毕设来说边际收益太低。

**架构上是为后续拆分留了路的**——两条业务域库表不交叉、模块独立、JWT 是无状态认证，未来要拆成"认证服务 / 考勤服务 / 实验室服务"门槛不高。

### Q34. 为什么没用 Spring Security / Shiro？
**答**：本系统权限粒度只到接口级别、角色只有 3 个，引入 Spring Security 需要配 SecurityFilterChain、UserDetailsService、AuthenticationProvider，复杂度提升明显。我用了一个**简洁的 JwtAuthFilter + UserContext + 显式 require 方法**的组合，行为可控、易调试、性能开销小。理论上一切 Spring Security 能做的，我现在的方案都能做，只是不如它"标准"。

### Q35. 数据库为什么不用物理外键？
**答**：项目当前**通过应用层 + JPA 实体映射 + 索引**保证关联，没有强制建立物理外键。原因：
- **解耦**：物理外键会让两条业务域强绑定，扩展和拆分都受限；
- **性能**：高并发写入时外键约束检查带来额外开销；
- **运维**：迁移、刷数、建测试库时外键约束容易出错。
当前数据量小，应用层校验完全够用；如果后续上生产、数据规模上来，可以补外键约束作为最后兜底。

## 十一、其他常见追问

### Q36. 三个角色为什么这么划分？admin 为什么不参与课程业务？
**答**：是迭代收敛的结果：
- 最初版本 admin 兼了"系统管理员 + 实验室管理员"两个身份，承担了用户管理、课表管理、考勤总览等职责，但**职责膨胀导致权限边界混乱**；
- 后来按"真实使用场景"重构：研究生管理学院里，**课程教学归教师管，实验室资源归实验室管理员管**，两类管理员是真实分工，没必要混在一个 admin 里；
- 当前 admin 专注于"实验室管理员"语义——维护实验室、审批预约、看使用统计。
这次重构在 `docs/角色统一为admin重构方案.md`、`docs/管理员端功能精简方案.md` 里有完整记录。

### Q37. 为什么时段是固定的 6 个 2 小时？不支持自定义？
**答**：
- **业务原型**：高校实验室开放管理实务中通常按"上午/下午/晚上"切几个固定时段，固定时段便于排课和统计；
- **冲突检测简单**：固定时段下"实验室 + 日期 + 时段"是离散的三元组，冲突判定一目了然；自定义时段会引入"区间重叠"判定，复杂度上升；
- **真实使用率统计**：分母容易聚合。

如果未来要支持自定义，需要在 `lab_booking` 表增加 `start_time` / `end_time` 字段，预约时做区间重叠判定（业务和 SQL 都要改）。当前实现明确**用固定时段换实现简单和可解释性**。

### Q38. 整个项目你做了多久？最难的部分是哪里？
**答**（可个性化）：
- 时间：从需求分析、设计、开发、测试到论文，大约 4 个月；
- 最难的部分：**实验室预约状态机的设计**——一开始只想着"申请 + 审批"，后来加了签到签退、爽约自动识别、自动完结，状态从 3 个扩到 7 个；要保证「冲突检测」和「真实使用率统计」对状态的语义判定一致（哪些状态占用时段、哪些状态算"已生效"、哪些状态算"实际使用"），这套状态语义需要前后端、Service、Repository、统计接口全部对齐。

### Q39. 论文里"7 个核心实体" 但数据库设计说明里有 8 张表，怎么解释？
**答**：诚实回答即可：
